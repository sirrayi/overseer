## 18. Frontends and Experience

### 18.1 Where we stand

A full-screen TUI with transcript scrolling, an inline mode, a plain-text REPL, and a hardened localhost web UI that streams the same surface; typed permission previews; rewind, diff with hunk-level rejection, fork tree, session picker, search; OSC notifications, prompt marks and file links; themes and reduced motion **[have]**. All of it assumes a run lives inside the frontend that started it.

### 18.2 Principles from the playbook

Cell-diffed rendering, synchronized output probed rather than guessed, a frame budget under 16.7 ms, O(1) per-token append, scrollback preservation, accurate interrupt affordance, contextual permission prompts, checkpoints and rewind, queued and editable messages, and a mode badge **[src: playbook thesis 9]**. Overseer already follows these. The new work is about long runs, many runs, and being away.

### 18.3 Workstreams

#### X1 — The long-run cockpit

**What.** One screen (TUI and web) for everything running: runs and workflow instances with state, health (B8), spend against budget, forecast, last milestone, next step, pending approvals and in-doubt effects; drill into a run's timeline (B3), journal, agent graph (O14) and transcript. Attaching to a detached run (R4) opens it here.

#### X2 — The inbox frontend

**What.** A7's inbox in the TUI and web UI: items grouped by urgency and source, with typed actions, previews, snooze, and receipts. The same items appear on Telegram and later in the Life app.

#### X3 — ACP and the editor bridge

**What.** ACP has become the editor protocol (about 35 agents, Zed and JetBrains as clients) **[src]**. A thin ACP adapter crate over `overseer-proto`, sync threads, no tokio, so Overseer runs inside editors; plus app-server parity for other clients.

#### X4 — Approvals and status from the phone

**What.** Telegram first (the channel exists): approve or reject with the preview, see run status, pause, resume, kill. Messages carry signed, expiring action tokens so a forwarded message cannot approve anything. Later the Life iPhone app takes over (F).

#### X5 — Notifications that respect attention

**What.** The EV gate (have) decides whether to interrupt; notifications are batched, deduplicated, quiet-hours aware (with real time zones, A5), and every notification links to the item it is about.

#### X6 — Steering long runs

**What.** Steering today is a queue checked at tool-launch boundaries. For long runs: steer messages land in the journal as owner notes (R5) so they survive compaction and resume; "change of plan" steers trigger a plan revision; steers to a specific graph node or persistent agent go to its mailbox (O17).

#### X7 — Web UI parity

**What.** Every TUI capability in the web UI, plus the views that need a canvas: timeline, graph, memory panel (M11), permissions page (P12), workflow editor with validation (A1).

#### X8 — Onboarding

**What.** The playbook's OpenCrane-style onboarding: a short interview → a draft persona and policy (consent mode, sensitive-surface permissions P6, budgets) → owner approval → each insight traceable to the answer that produced it.

#### X9 — Accessibility

**What.** Screen-reader-friendly output in the plain REPL (exists), high-contrast and mono themes (exist), keyboard-complete web UI, and ARIA roles in the web renderer.

#### X10 — Documentation as part of the product

**What.** Every workstream that changes behaviour updates the user-facing documentation in the same PR: the README, `overseer --help` and per-command help, a reference generated from the code for configuration keys, event kinds and policy syntax, and a short guide per major capability (long runs, workflows, policy, orchestration). `AGENTS.md` stays the contributor reference; decision records stay the "why".

::: gate
A doc check in the local gate: every configuration key, event kind and CLI command present in the code appears in the generated reference.
:::

#### X11 — Importing from other harnesses

**What.** Switching costs keep people on incumbents. `overseer import` brings readable state across: Claude Code and OpenCode session histories as read-only, replayable sessions (indexed by history search, M1), their memory and instruction files (CLAUDE.md is already covered by P1's compatibility imports), and their permission rules translated into rules v2 (P3) for review before activation. Imports are untrusted content until the owner approves them, and nothing is ever written back to the other tool's files (the standing Life rule).

::: note
Voice and other frontends named in the playbook's Alfred diagram are not planned in the harness. They belong to Overseer Life's later phases, which consume the harness through the SDK (Y4).
:::
