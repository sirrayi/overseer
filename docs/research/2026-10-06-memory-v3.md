builds on `2026-09-30-memory-v2.md`. v2 gave overseer a careful memory engine (ranked search, recall, reminders,
quarantine). what it doesn't do is learn on its own. v3 adds that, plus everything else worth taking from hermes
(nous research) and agent memory repo (cognition). sources were read in full on 2026-10-06:

not taken, on purpose:
- **external memory providers** (honcho, mem0…): no consumer yet. `// DEFERRED(owner): provider seam — gate: overseer life needs a remote store`.
- **embeddings / vector search**: same reasons as v2 (size, poisoning). bm25f + activation stay.
- **llm query rewrite before recall**: adds a model call to every turn. recall stays deterministic.
- **a forked agent with tools for the review** (hermes' shape): overseer's review is one bounded call that returns a
  line protocol the engine validates. no tool surface, nothing to escape, easy to test.

## 1. the review pass

### 1.1 what it is
after a run ends (the answer is already delivered), the engine may run one **review**: a single aux model call over a
digest of what happened since the last review. the model answers in a strict line protocol (§1.5). the engine
validates every line and applies it under the write policy (§1.6). the review never touches the conversation, so the
prompt cache and resume are unaffected. it is recorded as a `MemoryReview` event (audit only, not rehydrated).

### 1.2 when it runs
checked at every run end, first match wins:
1. **signal**: this run's user input carried a correction or an explicit "remember" (§1.3).
2. **turns**: ≥ `learn_every` user turns (default 6) since the last review.
3. **work**: ≥ 15 tool calls since the last review (procedural learning).
4. **before compaction**: right before `compact()` summarizes away events newer than the review cursor.
5. **explicit**: `overseer memory learn <session-dir> [--focus "..."]` (attended).

a review is skipped when: learning is off, the session is a subagent, `--bare`, memory is off, nothing new since
the cursor, or the run's remaining cost budget is below the review's worst-case cost. a skip with a reason is still
recorded (`MemoryReview { skipped: Some(reason) }`), so tuning is observable.

the agent's own `memory remember` calls reset the turn counter (hermes does the same: if the agent is already saving,
don't nag it).

### 1.3 learning signals (deterministic, no model)
on each user input the engine matches a small lexicon and records `LearnSignal { kind, excerpt }`:
- `remember`: "remember (that|this|to)", "from now on", "going forward", "next time", "always …", "never …",
  "don't ever", "keep in mind".
- `correction`: input starts with "no", "nope", "wrong", "stop", "don't", "actually"; or contains "that's (wrong|not)",
  "not like that", "you (keep|always|never)", "i (prefer|want|like|hate|told you)", "instead of", "too (verbose|long)".

case-insensitive, word-bounded, the excerpt is the matching sentence capped at 200 chars and redacted. false positives
cost one review call. false negatives fall back to the turn cadence.

### 1.4 the digest and the prompt
the engine builds the review input from the event log between the cursor and now:
- user inputs (redacted, ≤ 600 chars each), with signal markers;
- assistant final text per run (≤ 600 chars each);
- tool calls as `name(ok|error)` counts plus files touched (≤ 20), verify outcomes, stop reasons;
- **never tool result bodies** (that's where untrusted text lives);
- the ids of notes recalled in the window (candidates for FEEDBACK);
- the top 8 existing notes related to the digest (bm25 over the digest's terms), with id and 160-char snippet, so the
  model can SUPERSEDE or FEEDBACK instead of adding a duplicate;
- learned skills: name + description for all, plus the full current body of at most 2 learned skills that were loaded
  in the window (only those can be patched, §5.3).

the whole input is capped at 14,000 chars, oldest parts trimmed first. the prompt adapts hermes' review prompts
(attribution in the source file): which layer a fact belongs in (profile = who the user is, semantic = facts about the
environment and projects, procedural = how to do a class of task), procedure-first lessons with one clause of why,
no incident narration, ticket numbers or dates as content, the same lesson twice is one rule, and the do-not-capture
list (environment-dependent failures, negative claims about tools, transient errors, one-off narratives, unresolved
failures dressed up as a method). corrections are first-class. NOTHING is allowed but not the default when a signal
fired.

### 1.5 the line protocol
one op per line. a body block follows a SKILL or PATCH-SKILL line, between `<<<` and `>>>` lines.

```
ADD <layer> <slug> :: <text> [:: cues=<a,b>]
SUPERSEDE <scope:layer/name.md> :: <new text>
FORGET <scope:layer/name.md> :: <reason>
FEEDBACK <scope:layer/name.md> helpful|wrong
SKILL <slug> :: <one-line description>
PATCH-SKILL <slug> :: <one-line summary of the change>
NOTHING
```

validation (engine, every line; a bad line is rejected and counted, the rest still apply):
- at most 6 ops per review, at most 2 of them SKILL/PATCH-SKILL;
- ADD layers: `semantic`, `procedural`, `profile` (never `episodic` or `prospective` from a review);
- slugs: lowercase `[a-z0-9-]`, 3–48 chars, not all digits, no ticket-like names (`pr-123`, `issue-45`, `fix-*` for a
  one-off) → rejected;
- note text ≤ 600 chars, skill body ≤ 8,000 chars, description ≤ 160 chars;
- every text and body passes `redact::scrub` and the threat scan (§3); a strict-scope hit rejects the op;
- SUPERSEDE/FORGET/FEEDBACK targets must exist and be current; duplicates of an existing body are rejected as dupes.

### 1.6 write policy (unattended review)

| op | taint-free window | tainted window (a `Tainted` event in the window) |
|---|---|---|
| ADD semantic/procedural | applied, `confidence: 0.6`, `provenance: review:session:<id8>`, `source:` link | quarantined to `proposals/` (v2 rule) |
| ADD profile | staged (profile writes need approval, v2 write bar) | quarantined |
| SUPERSEDE, FORGET | staged (hermes: unattended reviews never replace or remove) | rejected |
| FEEDBACK | applied: helpful +0.05 (cap 0.95), wrong −0.15 (floor 0.1); a `wrong` on a note below 0.3 stages a FORGET | rejected |
| SKILL (new learned skill) | applied as `status: probation` | rejected |
| PATCH-SKILL (learned skill only) | applied with a ledger entry (rollback-able) | rejected |

`--learn-stage` (config `learn_stage`) stages everything instead. an attended review (`overseer memory learn`) applies
SUPERSEDE/FORGET directly, the way hermes' `/refine` keeps the full op set. user-authored skills and workspace skills
are never written by a review.

### 1.7 cost and model
the review uses `small_model` when set, else the main model, `max_tokens` 1,200, effort min. unlike today's
`aux_call`, the review call **is ledgered** (purpose `memory_review`) and counted against the run's cost budget
(invariant 3). one call per review, no retries beyond the existing small→main escalation.

### 1.8 cursor
`MemoryReview { through }` is the id of the last event the review covered. on resume the cursor replays from the log,
so a window is never reviewed twice.

## 2. pending queue (approvals)
- `<store>/pending/<id>.json`: `{id, op, target, target_sha256, payload, origin, reason, created}`. ids are short and
  unique. proposals from tainted windows stay in `proposals/` as v2 has them, and `pending` lists both.
- approve applies only when the target's current content hash equals `target_sha256` (hermes pins the full target
  entry). otherwise it refuses and the item stays pending until rejected.
- `overseer memory pending`, `overseer memory approve <id|all>`, `overseer memory reject <id|all>`.
- approving a proposal from `proposals/` promotes it into its layer with `confidence: 0.5` and a provenance note.

## 3. threat scan
port hermes' `tools/threat_patterns.py` to `crates/overseer-core/src/memory/threat.rs` with the MIT notice:
the same pattern table (scopes `all`, `context`, `strict`), invisible/bidi unicode detection, a 64 KiB scan cap, and
the bounded-filler regex shape. `regex-lite` is already a dependency. adapt the hermes-specific paths
(`~/.hermes/.env`, `.hermes/config.yaml`) to overseer's (`~/.overseer/`, `AGENTS.md` writes stay). every memory write
path (tool remember, review ops, learned skills, approvals, mounted-repo writes) runs the strict scan. a hit refuses
the write with the pattern id. the scan is advisory for recall output and history output (`context` scope): hits are
flagged in the wrapper, never silently dropped.

## 4. `memory op=history`: search past sessions
hermes' `session_search`, built on overseer's own bm25f engine.
- **source**: every parent session under the sessions root (`~/.overseer/sessions/*/events.jsonl`), newest 400
  sessions or 64 MB read, whichever comes first; subagent logs and the current session are excluded.
- **unit**: one doc per user turn: the user input plus the assistant text until the next input (≤ 4,000 chars), fields
  user text (boost 3), first prompt of the session (2), assistant text (1). tool result bodies are never indexed.
- **ranking**: rrf over bm25f, recency, and same-project (session cwd equals the current project key).
- **shapes** (inferred from args, like hermes):
  - `{query}`: top 5 sessions, deduped by session. the best one comes with ±2 turns, the others with one snippet each;
  - `{session, around}`: ±`window` turns (default 3, max 8) around a turn id;
  - `{session}`: head and tail turns of a session (bounded);
  - `{}`: the 15 most recent sessions (date, project, first prompt).
- output ≤ 8,000 chars, redacted, provenance-wrapped as `history`, threat-flagged (§3). history reads are not memory
  "uses" (no activation bump). built lazily on the first call, refreshed by mtime.
- schema: `op` gains `history`, plus optional `session`, `around`, `window`. `scope` becomes a free string
  (`user`, `project`, `repo:<name>`). the resident spec grows a little and the startup-budget pin is updated with
  this record as the reason.

## 5. learned skills
### 5.1 where and what
- learned skills live in the user skills root `~/.overseer/skills/<slug>/SKILL.md` with extra frontmatter:
  `created_by: overseer-learn`, `status: probation|active|stale`, `provenance: review:session:<id8>`,
  `confidence`, `pinned: false`.
- a skill without `created_by: overseer-learn` is user-owned. reviews and the curator never touch it.
- the skills index (`skills.rs`) shows learned skills with a `(learned)` tag, skips `.archive/`, and still loads bodies
  provenance-wrapped.

### 5.2 ledger and rollback (hermes `skill_ledger.py`)
every learned-skill write appends to `~/.overseer/skills/.ledger.jsonl`: `{id, ts, op, skill, before_sha, after_sha,
origin}`, with blobs stored content-addressed under `~/.overseer/skills/.ledger/blobs/<sha>`.
`overseer memory skills rollback <id>` restores the before blob, refusing if the skill changed since that entry.

### 5.3 usage and patches
- loading a skill through the `skill` tool records a use in `~/.overseer/skills/.usage.json` (`uses`, `last_used`),
  written atomically under the write lock.
- PATCH-SKILL replaces the body of a learned skill only if the review prompt included that skill's current body and
  its sha still matches (read-before-write, the hermes guard).

### 5.4 lifecycle (deterministic, run by the dream pass)
probation → active after ≥ 2 uses with no `wrong` feedback; active → stale after 30 days unused; stale → archived after
60 more days unused (moved to `~/.overseer/skills/.archive/<slug>-<date>/`, never deleted); pinned skips everything;
a probation skill unused for 30 days is archived.

## 6. the dream pass
`overseer memory dream [--dry-run] [--unattended]` extends today's `consolidate`:
1. v2 consolidate: index dedupe (llm), use-journal compaction, episode distillation (llm).
2. exact duplicates within a store and layer: keep the oldest, supersede the rest (deterministic, applied).
3. near duplicates and contradictions: note pairs in the same layer with term jaccard ≥ 0.6 go to one llm judge call
   (≤ 10 pairs) answering `MERGE a b :: text`, `CONTRADICT a b :: keep a|b`, or `KEEP a b`. the judge may read the
   `source:` turns of both notes through the history index, the "check sources" step from agent memory repo.
   attended runs apply the answers. unattended runs (the daemon) stage them.
4. fade: semantic/procedural notes with activation below −2.5, older than 120 days, confidence ≤ 0.6, not pinned →
   expired with `forgotten: faded` (reversible with `overseer memory restore`).
5. learned-skill lifecycle (§5.4).
6. regenerate `MEMORY.md`, commit each store, write `<store>/.index/dream.json` (last run, counts).

**startup subset**: at the first user input of a session, if the last dream is older than 48 hours, steps 2, 4, 5 and 6
run synchronously. they're deterministic and need no model. **daemon**: a new gateway trigger
`{"kind":"maintenance","id":…,"expr":"0 4 * * *","task":"memory-dream"}` spawns `overseer memory dream --unattended`.

## 7. recall tweaks
- trivial prompts skip recall: empty, slash commands, or a bare acknowledgement ("ok", "thanks", "continue", "lgtm",
  … the hermes list).
- recall output also passes the context-scope threat scan and flags hits.

## 8. inspection
- `overseer memory stats`: notes per store and layer, pending, proposals, learned skills by status, last review and last dream.
- `overseer memory log [--store user|project]`: git log of the store, newest first.
- `overseer memory restore <scope:layer/name.md>`: clears `valid_to`/`forgotten` on an expired note.
- a `MemoryLearned` summary line rides the `MemoryReview` event for the tui/web to show later (frontend stage).

## 9. agent memory repo compatibility
### 9.1 `MEMORY.md`
each store gets a generated, committed `MEMORY.md` that follows the AMR spec: `# Memory: <store>`, the CORE.md lines as
top bullets, then `## Index` with `- [[layer/name]] — title` for every live pointer (no `.md` suffix, as the spec
says). before regenerating, if `MEMORY.md` differs from the hash of the last generated file (someone, maybe a devin
session with the AMR skill, edited it), new bullet lines are imported into `semantic/amr-import-<date>.md` with
`provenance: amr-import` and `confidence: 0.5`, then the file is regenerated.

### 9.2 `source:` and `added:`
notes gain two frontmatter keys: `source: overseer:session/<id>#e<event>` and `added: YYYY-MM-DD`. tool and review
writes set both. `MEMORY.md` bullets render them in AMR form `[source: …; added: …]`.

### 9.3 commit after every write
tool writes and review writes commit the store right away (`memory: remember …`, `review: …`). the turn-boundary
commit stays as a backstop. all store writes take `<store>/.index/write.lock` (create-new lock file with pid and time,
stale after 30 s), so two sessions can't interleave writes.

### 9.4 mounted memory repos
- config `~/.overseer/memory-repos.json`: `[{name, path, owned, trust, remote?, sync_on_start?}]`, plus flag
  `--memory-repo <name>=<path>` (repeatable, read-only, untrusted).
- a mounted repo is indexed like AMR expects: `MEMORY.md` and every `*.md` under it. one doc per file, bullets kept.
  ids look like `repo:<name>:<path>`. search, get and recall include mounts.
- `trust: untrusted` (the default when not owned) means reading a mount sets the untrusted latch, like any outside
  content. `trust: read` doesn't.
- writes go only to `owned: true` mounts: `remember scope=repo:<name>` appends an AMR bullet
  `- <text> [source: …; added: …]` to `<slug>.md` (linked from the `## Index` in `MEMORY.md`) and commits right away.
  a dirty worktree refuses the write and says what is uncommitted (the AMR "clean before writing" rule).

### 9.5 sync
`overseer memory sync [--store user|project|repo:<name>]`: `git pull --ff-only`, then `git push` when a remote is
set. it never forces and never merges on its own, refusing on a dirty tree or a non-fast-forward. `sync_on_start`
does the pull only, with a 10 s timeout. there's no automatic push.

## 10. new events and flags
- events (audit only, old logs still replay):
  - `LearnSignal { kind, excerpt }`
  - `MemoryReview { trigger, through, applied, staged, quarantined, rejected, skipped, model, cost_usd }`
- AgentConfig: `learn: bool` (default on when memory is on, off for `--bare`/subagents), `learn_every: u32` (6),
  `learn_stage: bool` (false).
- flags: `--no-learn`, `--learn-every <n>`, `--learn-stage`.

## 11. verification
deterministic, no live model, no spend:
- unit tests per module: lexicon, digest bounds, protocol parser (every rejection rule), write policy table (every
  row and column), pending pin and refusal, threat scan (each pattern id, the invisible chars, no false positive on a
  plain AGENTS.md), history shapes and caps, ledger and rollback, lifecycle transitions, dream steps, MEMORY.md shape
  and import, lock contention, sync refusal cases.
- end to end with a scripted mock provider:
  - session A has a correction → the review ADDs a procedural note → session B's recall surfaces it;
  - a tainted session → the review output is quarantined;
  - a threat-pattern ADD is rejected;
  - FEEDBACK moves confidence;
  - a staged SUPERSEDE approves once and refuses after the target changes;
  - history finds session A's turn;
  - the dream merges an exact duplicate;
  - a learned skill goes probation → active after two loads;
  - `MEMORY.md` is AMR-valid (exists, `## Index`, every `[[link]]` resolves);
  - the review cost lands in the ledger.
- gates: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`,
  `cargo deny check`.

deferred:
- live runs with a real model, and LongMemEval-S (owner: benchmark hold);
- an external provider seam;
- frontend surfaces (`/learn`, `/memory pending`, a learning timeline).
